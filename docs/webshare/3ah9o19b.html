1전체 구성도

BSP는 하나(메시지면 + 통화·미디어면). 서비스서버가 오케스트레이터, AI 4종은 서버 허브로 연결.

제어/데이터 통화·오디오 미디어 개인 메세지/통화 (API 없음)

BSP(call) = WABA 안에 포함

  • BSP(call)은 별도 업체가 아니라 같은 BSP·같은 WABA 계정의 통화 API 면. 메시지면과 통화·미디어면으로 표면만 다름.
  • 다만 책임·역량 확인은 면별로 다름: 메시지면(템플릿·콜버튼)은 표준, 통화·미디어면(RTP 브릿지·채널 포킹·STT)은 BSP별 [확인필요].

2콜 셋업 콜플로우 (딥링크 기준)

축소 플로우: A 1탭(B지정+콜레그 선개통, ①+⑧ 결합) → 개인창 전송 1탭 → B 1탭(고지 포함 링크=동의+진입, S1+S2 통합) → 브릿지. A 2동작 / B 1동작.

동작 수 — A 2 / B 1 (축소 적용)

  • A 2동작: ① B 지정+콜레그 선개통(통화 탭 흡수) · ④ 개인창 전송 1탭. ④는 개인창 API가 없어 제거 불가 = 아웃바운드 최소치.
  • B 1동작: ⑤ 고지 포함 메시지의 "통화(녹음동의)" 링크 탭 = 동의+진입(별도 동의 화면 제거). IVR DTMF 재동의가 법적 증적 백업.
  • 트레이드오프: A 콜레그 선개통으로 B 진입까지 "연결 중…" 대기 발생(타임아웃·WABA 콜세션 유지시간 관리 전제).
  • 인바운드(QR/공개토큰): B가 먼저 스캔·진입 → A는 통화 응답 1동작, ④ 불필요 → 6번 재사용 섹션 참조.

4통화종료 후 AI요약 콜플로우 (시나리오 ②)

종료 시점부터 전사·요약·전달. A-ixio·B-ixio 창은 세션 내 무료 전달, A-B 개인창은 ④에서 미리 보낸 요약 웹링크가 채워짐.

5요약 전달 방식 — 개인창 & 요약 웹링크

A-B 개인창 자동 기록은 불가 → 요약 웹링크로 해결

  • 직접 기록 불가: A↔B 개인 채팅은 E2E·API 없음 → 서버가 텍스트를 써 넣을 수 없음.
  • 해결(채택): 최초 콜링크 메시지에 요약 permalink(예: s.ixio/<token>)를 함께 발송 → 통화 후 서버가 그 URL에 요약을 채움 → A·B는 개인창에 이미 있는 링크를 탭해 열람. WABA 비용 0.
  • 3곳에서 동일 접근: A-B 개인창(링크), A-ixio 창(요약 메시지+링크), B-ixio 창(요약 메시지+링크).
  • PDPA 조건: 토큰은 추측 불가(난수), 만료·1회성/로그인 게이트, 접근 로그, 삭제 시 링크 무효화. 요약 본문에 민감정보 최소화.

6통화링크 재사용 — 연락처 저장 · 상시 QR · 토큰 3종

1회용 세션 토큰을 재사용 가능한 토큰으로 설계하면, 매번 딥링크를 새로 보내지 않아도 통화 시작 가능.

재사용 방식 3갈래

  • 연락처 저장(특정 B): A가 vCard 공유 시 통화 링크를 URL/메모 필드에 포함 → B가 연락처로 저장, 탭마다 새 통화. (WhatsApp에 전용 통화버튼 필드는 없어 URL 방식이 현실적)
  • 상시노출 QR(불특정 다수) · 권장: A-공개 토큰을 QR로 발급 → 명함·이메일 서명·매장 게시. B 스캔 = ixi-O 진입(user inbound·무료·옵트인 불필요) → 동의 → A 호출. biz 포지셔닝 최적, A의 딥링크 전송(④) 불필요.
  • 페어 영구 링크(1:1): A↔B 최초 교환 후 그 링크를 B가 저장해 재사용.

7미디어 제어 — 서버가 직접 해야 하나?

권장: 서버는 오케스트레이션만, 저수준 미디어는 BSP 위임. BSP 역량에 따라 3단계로 분기(현 미결 블로커가 이 분기를 결정).

모델BSP 역량서버 역할부담
T1 · 완전 위임권장브릿지 + 채널 포킹 + STT 모두 지원API 호출·이벤트 구독만(콜 생성/bridge/say). 전사 결과 수신 → 요약낮음
T2 · 부분 위임브릿지 O · STT XBSP가 채널 오디오를 우리 STT로 포워딩 → 서버는 경량 미디어 중계·정렬중간
T3 · 자체 미디어브릿지 X (2안 직접)서버가 RTP 포워딩·SRTP 종단·채널 분리 직접 운영(미디어 서버 필요)높음
④음성비서·⑤대신받기는 통화 중 양방향 실시간 오디오(저지연 in/out·TTS 주입)가 필수 → 최소 T1~T2의 실시간 스트림·barge-in 지원 필요.
결론: 정상 경로는 서버가 미디어를 직접 다루지 않음(T1). T3는 BSP가 브릿지조차 불가할 때만. 미결 블로커(RTP 포워딩·포킹 STT) 확인이 모델을 확정.
